# VelaRi 0.4 Design and Implementation Plan

**Status:** Design baseline

**Target milestone:** VelaRi 0.4

**Primary outcome:** Move VelaRi from a dynamically represented interpreter foundation toward a typed compiler front end with explicit collection types and a backend-neutral intermediate representation.

## Executive summary

VelaRi 0.4 should establish the compiler boundaries that later native code generation will depend on. The milestone should not begin with GUI APIs or platform packaging. It should first make types, scopes, diagnostics, and lowering contracts explicit.

The recommended sequence is:

1. Stabilize the source model and diagnostic APIs.
2. Add explicit type annotations and type expressions.
3. Replace the current lightweight semantic pass with a typed abstract syntax tree.
4. Represent arrays and maps as parameterized collection types.
5. Introduce a backend-neutral intermediate representation.
6. Preserve the interpreter by lowering the typed representation into the existing runtime evaluator.
7. Add conformance tests before beginning native LLVM lowering.

This sequence reduces risk because every later backend can consume the same validated typed representation.

## Goals and non-goals

| Area | VelaRi 0.4 goal | Explicitly deferred |
| --- | --- | --- |
| Type system | `Int`, `Float`, `Bool`, `String`, `Char`, `Null`, `Array<T>`, `Map<K,V>`, and function types | Generics beyond collection parameters, traits, and user-defined types |
| Syntax | Type annotations, collection literals, indexing, calls, assignment, and returns | Pattern matching and operator overloading |
| Compiler model | Typed AST and backend-neutral IR | Complete LLVM/native code generation |
| Runtime | Safe interpreter support for typed values and collection operations | GUI, networking, filesystem, processes, and asynchronous runtime |
| Tooling | Stable diagnostics and focused compiler tests | Language server and formatter |
| Branding | Technical names and stable CLI terminology | Final logos, banners, icons, and visual identity |

## Current baseline

The current repository contains a lexer, Pratt-style parser, semantic analyzer, tree-walking interpreter, CLI, examples, and release workflow. The interpreter supports functions, lexical scopes, assignment, arrays, maps, indexing, and `length`. The current implementation still represents semantic types as a small enum and does not preserve resolved types in the AST. The current parser also returns syntax errors separately from a reusable diagnostic abstraction.

The 0.4 design should preserve the user-visible syntax that already works while replacing internal representations incrementally. Existing examples must remain valid unless a deliberate language change is documented.

## Proposed source language

### Type annotations

The annotation grammar should use a single type-expression form:

```velari
let count: Int be 3
let title: String be "VelaRi"
let values: Array<Int> be [1, 2, 3]
let users: Map<String, Int> be {"admin": 1}
```

Annotations constrain inference. They do not disable inference for unannotated declarations.

```velari
let count be 3              # inferred as Int
let values be [1, 2, 3]     # inferred as Array<Int>
```

The parser should preserve the annotation in the AST. The semantic pass should validate that the initializer is assignable to the declared type.

### Numeric policy

VelaRi should distinguish integers from floating-point values in 0.4.

| Literal | Type |
| --- | --- |
| `42` | `Int` |
| `42.5` | `Float` |
| `true` and `false` | `Bool` |
| `"text"` | `String` |
| `null` | `Null` |

Implicit numeric conversion should not be introduced yet. An explicit conversion API can be added after the type checker and backend agree on integer widths.

### Function types

Functions should have parameter and return types in the typed AST even if the source annotation is omitted.

```velari
function add(a: Int, b: Int): Int
    return a + b
end
```

For the first typed implementation, functions should remain declarations rather than first-class closure values. The AST should nevertheless reserve a function-type representation so closures can be added without redesigning all expression nodes.

### Collection rules

Arrays must contain one element type. Maps must have one key type and one value type.

```text
[1, 2, 3]                  -> Array<Int>
{"name": "VelaRi"}        -> Map<String, String>
```

An empty collection requires an annotation because it has no element evidence:

```velari
let values: Array<Int> be []
let names: Map<String, String> be {}
```

Indexing rules should be checked statically whenever the collection type is known:

```text
Array<T>[Int]       -> T
Map<K,V>[K]          -> V
```

The runtime must still perform bounds and key-existence checks.

## Internal architecture

### Pipeline

```text
Source text
   │
   ▼
Lexer ──► Token + Span
   │
   ▼
Parser ──► Untyped AST
   │
   ▼
Name resolution ──► Symbols, scopes, function declarations
   │
   ▼
Type checking ──► Typed AST
   │
   ├──────────────► Interpreter evaluator
   │
   ▼
Lowering ──► VelaRi IR
   │
   ▼
Future native backends
```

Name resolution and type checking should be separate passes. This separation makes forward function references possible and prevents the type checker from carrying unresolved identifier logic.

### Typed AST

The typed AST should attach a resolved `Type` to every expression and declaration.

```rust
pub enum Type {
    Int,
    Float,
    Bool,
    String,
    Char,
    Null,
    Array(Box<Type>),
    Map(Box<Type>, Box<Type>),
    Function { parameters: Vec<Type>, result: Box<Type> },
    Unknown,
}
```

The concrete Rust representation can evolve, but the semantic invariant should remain: a successfully checked expression has one resolved type.

### Scope model

Scopes should be explicit objects rather than directly exposed hash maps.

```rust
pub struct Scope {
    parent: Option<ScopeId>,
    symbols: HashMap<String, SymbolId>,
}
```

Each symbol should record its declaration span, type, mutability, and kind. The initial symbol kinds are variable, parameter, and function.

| Symbol property | 0.4 behavior |
| --- | --- |
| Declaration | A name may be declared once per scope |
| Shadowing | Inner scopes may shadow outer variables deliberately |
| Assignment | Only declared mutable variables may be assigned after declaration |
| Parameters | Parameters are local immutable bindings initially |
| Functions | Functions are registered before body analysis to support recursion |

Mutability should be added explicitly rather than inferred from assignment. The proposed syntax is:

```velari
let mut counter be 0
counter = counter + 1
```

If mutability is not implemented in the first 0.4 slice, assignments should remain supported only for compatibility and be marked for tightening in the next breaking language revision.

## Diagnostic system

Diagnostics should become a first-class compiler API shared by lexing, parsing, name resolution, and type checking.

```rust
pub struct Diagnostic {
    pub severity: Severity,
    pub code: DiagnosticCode,
    pub message: String,
    pub primary: Label,
    pub secondary: Vec<Label>,
    pub notes: Vec<String>,
    pub help: Option<String>,
}
```

The renderer should support terminal text first. JSON output can follow once the diagnostic model is stable.

Recommended initial codes:

| Code | Meaning |
| --- | --- |
| `E1001` | Unexpected character |
| `E2001` | Syntax error |
| `E3001` | Name resolution error |
| `E3002` | Type mismatch |
| `E3003` | Invalid assignment |
| `E3004` | Invalid function call |
| `E3005` | Invalid collection index |

Every diagnostic should include a primary source label. Type errors should include the expected and found types in a note or secondary label.

## VelaRi intermediate representation

The IR should be deliberately smaller than the source AST. It should contain explicit control flow and typed operations.

```text
Function add:
  block0:
    %a = parameter 0 : Int
    %b = parameter 1 : Int
    %sum = add_int %a, %b
    return %sum
```

The first IR instruction set should include:

- Constants for each primitive type
- Local allocation, load, and store
- Integer and floating arithmetic
- Boolean equality and logical operations
- String and collection runtime calls
- Function calls and returns
- Conditional branches
- Unconditional branches
- Bounds-checked indexing operations

The IR should not encode operating-system APIs. Filesystem, networking, windows, and process operations belong to runtime interfaces above the backend.

## Implementation phases

### Phase 0: Stabilization

Create golden tests for all existing examples and record the current CLI behavior. Separate parser diagnostics from semantic diagnostics. Keep the interpreter as the reference execution engine.

### Phase 1: Type syntax and primitives

Add type-expression parsing, integer literals, `Char`, explicit annotations, and assignability checks. Update the interpreter value model to distinguish integer and floating-point values.

### Phase 2: Typed collections

Add `Array<T>` and `Map<K,V>` type construction, empty-collection annotations, homogeneous literal checking, typed indexing, and `length` validation.

### Phase 3: Name resolution and function typing

Add symbol IDs, function signatures, recursive declarations, argument type checking, return-path validation, and duplicate declaration diagnostics.

### Phase 4: Typed AST

Lower the checked AST into typed nodes. The interpreter should consume typed expressions where possible so runtime checks become defensive assertions rather than the primary type system.

### Phase 5: IR and interpreter lowering

Introduce the IR data model and lower the typed AST into IR. Execute IR with the existing interpreter runtime or use the IR as a validation-only backend initially.

### Phase 6: Native backend preparation

Define target configuration, runtime ABI boundaries, and primitive type mappings. Native code generation should begin only after IR tests cover functions, branches, loops, strings, arrays, and maps.

## Testing strategy

The project should move from isolated unit tests to layered compiler tests.

| Test layer | Coverage |
| --- | --- |
| Lexer tests | Token sequences, spans, malformed literals, comments |
| Parser tests | AST shape, precedence, functions, collections, recovery |
| Semantic tests | Type inference, annotations, scopes, calls, indexing, diagnostics |
| Interpreter tests | Values, runtime errors, recursion, collections, control flow |
| CLI tests | `check`, `run`, `new`, version output, exit status |
| Golden tests | Complete diagnostic text and example output |
| Property tests | Parser never panics on arbitrary token sequences |

Every bug fixed from `ISSUES.md` should become a regression test before the issue is closed.

## Acceptance criteria for VelaRi 0.4

VelaRi 0.4 is ready when the following conditions hold:

1. Existing 0.3.1 examples continue to check and run.
2. Explicit primitive and collection annotations are parsed and checked.
3. Array and map literals reject incompatible element types.
4. Function calls validate argument count and argument types.
5. Recursive functions resolve correctly.
6. Scope errors identify the declaration and use sites.
7. Diagnostics render stable source snippets with codes.
8. The typed AST contains no unresolved expression types after successful checking.
9. At least one backend-neutral IR example can be inspected in a test.
10. The release includes updated documentation and a migration note.

## Parallel branding handoff

Branding work can proceed independently from the compiler architecture. The technical project should use stable text-only names while visual assets are being designed.

| Asset | Recommended deliverable | Technical use |
| --- | --- | --- |
| Logo | SVG with light and dark variants | README, release page, future tooling |
| Repository banner | Wide PNG or SVG with a safe center area | GitHub social preview |
| Language icon | Square SVG and PNG | File association, editor extension, CLI package |
| Syntax icon | Small monochrome SVG | Documentation and syntax highlighting |
| Color tokens | Named palette with contrast notes | Future compiler UI and website |
| Wordmark | Vector wordmark with clear-space guidance | README and project website |

Asset filenames should be stable and platform-neutral. Recommended names are `velari-mark.svg`, `velari-wordmark.svg`, `velari-banner.svg`, and `velari-icon.svg`. The compiler should not depend on these assets, and source code should not embed temporary branding decisions.

## Decision log

| Decision | Rationale |
| --- | --- |
| Preserve the current readable syntax | Existing examples and users should not be forced through an unnecessary syntax rewrite. |
| Separate name resolution from type checking | The separation supports recursion, better diagnostics, and future modules. |
| Introduce IR before LLVM lowering | A stable IR prevents source-language changes from coupling directly to LLVM APIs. |
| Keep the interpreter as a reference backend | The interpreter provides fast feedback while native compilation is developed. |
| Defer GUI and OS services | Those APIs depend on stable types, permissions, and runtime ABI boundaries. |
